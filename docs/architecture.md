# 高层架构

本文描述 Wardrobe Mate 的目标架构和职责边界，不是已完成的工程设计。当前起步代码采用单文件 FastAPI 后端和进程内存储，尚未接入下文规划的持久化、用户隔离或外部服务。

## 架构原则

1. **端侧重交互。** 衣橱浏览和自由搭配是核心体验，优先保证图片展示与画布操作流畅；适合端侧完成的图像处理优先在设备上进行。
2. **后端保持轻量。** 后端承担业务数据管理、外部服务协调和推荐流程，早期不引入自建 GPU 服务或模型训练体系。
3. **AI 能力接口化。** 图像识别、必要的图像处理及语言生成通过外部服务接入，保留替换服务商的空间。
4. **规则与大模型协作。** 先处理衣物可用性、环境和搭配约束，再按需使用大模型辅助排序与解释。
5. **按实际需要扩展。** 缓存、向量检索、离线素材管线等能力在存在明确需求后引入。

## 模块职责

| 模块 | 主要职责 |
| --- | --- |
| 移动客户端 | 衣物采集与编辑、数字衣橱、搭配画布、穿着记录和反馈交互 |
| 业务后端 | 衣物与搭配管理、用户数据访问边界、外部服务协调、推荐流程 |
| 图像与属性处理 | 背景处理、主色分析、衣物属性建议和结果确认 |
| 推荐能力 | 环境与衣物约束、候选搭配生成、偏好排序、建议解释 |
| 数据与图片存储 | 保存业务记录、图片及后续检索所需的信息 |
| 外部服务 | 提供天气、图像识别或处理，以及可选的语言模型能力 |

这些是职责划分，不预设必须拆成多个独立服务。初期优先保持结构简单。

## 主要数据流

### 衣物录入

用户导入照片，客户端尽可能完成适合端侧的处理。后端协调必要的图片分析与 AI 属性建议，结果由用户确认或修正后纳入衣橱。

主体提取能力取决于设备、操作系统和图片质量。端侧能力不足时，可评估按量调用外部图像服务；不预先承诺所有设备均支持离线处理。

主色分析与服装语义识别分开考虑。照片光照、白平衡和材质可能影响颜色结果，用户能够纠正系统建议。

### 手动搭配

用户从衣橱选择衣物，在端侧画布调整大小、位置、角度和遮挡顺序。保存的搭配需要能够再次编辑，并支持导出图片。

画布交互不依赖实时调用大模型。

### 日常推荐

推荐过程先结合天气、场景、个人体感和衣物状态筛选候选，再考虑配色、廓形、风格、重复穿着和个人偏好形成搭配。

大模型可以辅助解释或排序，但最终结果需要满足真实衣物、当前可用状态及用户锁定单品等约束。它不能自行创造衣橱中不存在的单品。

外部 AI 暂时不可用时，可返回满足基本约束的建议；天气信息缺失时，应提示用户并允许补充条件。无法满足条件时，明确说明候选不足。

## 核心数据概念

| 概念 | 记录的内容 |
| --- | --- |
| 用户与偏好 | 使用者及其场景、风格和个人体感偏好 |
| 衣物单品 | 衣物图片、分类、属性，以及可用状态和穿着情况 |
| 穿搭组合 | 一套搭配包含的衣物、可编辑的画布状态与适用场景 |
| 穿着记录与反馈 | 实际穿着、当时环境和用户反馈 |
| 搭配模板 | 后续可能引入、来源和可用范围明确的抽象搭配规律 |

衣物属性按用途区分：用于筛选的基础属性、用于搭配判断的审美属性，以及后续可能用于语义检索的描述。需要采用一致的分类词汇，避免同义名称造成混乱，同时允许修正识别错误。

搭配模板和语义检索属于可选扩展，不是首版必须建设的数据能力。此处不定义数据库表、字段、索引或向量维度。

## 候选技术方向

以下内容沿用原始构想中的优先方向，尚未进行工程验证，不代表最终锁定选型。

| 层级 | 优先考虑的方向 | 需要验证的重点 |
| --- | --- | --- |
| 移动端 | Flutter，状态管理可考虑 Riverpod | 画布手势、图片处理、设备兼容性和团队熟悉度 |
| 业务后端 | Python / FastAPI | 业务维护成本、外部服务协调和图像处理需求 |
| 业务数据 | PostgreSQL，可评估托管服务 | 数据一致性、访问隔离、维护成本与部署地区 |
| 图片存储 | 托管对象存储，按需配合内容分发 | 私有图片访问、删除边界、存储与流量费用 |
| 缓存 | 必要时引入 Redis | 是否存在需要缓存的热点与重复外部请求 |
| AI 识别 | 通过多模态模型 API 获取属性建议 | 结果可用性、结构一致性、延迟、费用和数据流向 |
| 天气 | 第三方天气服务 | 目标地区覆盖、数据质量、定位选择与费用 |
| 语义检索 | 后续按需评估 PostgreSQL 的向量能力 | 参考图复刻和相似单品查找是否有足够价值 |

服务商、模型版本、价格和系统兼容范围，需要在实施前根据目标地区及当时的官方信息确认。

## 成本与可靠性方向

- 尽量复用已有识别结果，避免每次推荐都重复处理整个衣橱的图片。
- 外部图像和模型调用需要有明确用途，评估调用次数、失败成本与预算。
- 识别结果允许人工修正，外部服务失败时保留继续完成任务的路径。
- 业务数据与图片的访问需要按用户隔离，避免在公开资源中暴露私人衣橱。
- 托管服务优先作为减轻运维负担的候选，但仍需评估费用和数据管理责任。

端侧计算也会消耗设备资源和开发维护成本；外部服务费用、处理速度与识别质量以实际验证为准。
